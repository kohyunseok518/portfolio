콕찔러보기 — 대학 축제 소개팅 서비스

서로 "콕"을 보내면 매칭되어 채팅방이 열리는 서비스입니다. 축제 3일 동안 실제로 운영했습니다.

한눈에 보기

맡은 일 팀장으로 백엔드 API와 실시간 채팅, AWS 인프라와 배포, 부하 테스트, 행사 운영을 맡았습니다. 백엔드 저장소 커밋 128개 중 123개가 제 커밋입니다(병합 커밋 제외).

  • 실제 운영축제 3일, 가입자 445명 · 매칭 463건 · 채팅 메시지 6,156건
  • 실제 운영요청 44만 건 중 배포 시각을 뺀 서버 오류 8건(0.002%). 배포 순간 연결 실패 381건은 따로 기록하고 개선 과제로 남김
  • 부하 테스트900명 + 채팅 450명 조건에서 느린 쪽 5% 응답 시간 0.98초 → 0.07초, 필요한 서버 4대 → 2대
  • 부하 테스트콕만 보낸 측정에서 처리 한계 초당 40~50건 → 60~90건(다른 요청이 섞인 측정에서는 46~56건)

인원BE 2명 / FE 2명
스택Java 21, Spring Boot 3, JPA, MySQL 8.4, Redis, WebSocket(STOMP), Flyway, AWS(ALB, Auto Scaling, RDS, ElastiCache), GitHub Actions, Next.js

이력서에 적은 내용

  • 쿼리별 DB 시간을 재서 탐색 목록 10초 캐시·DB 명령 40% 축소, 900명 부하에서 p95 0.98초 → 0.07초, 서버 4대 → 2대
  • 콕 한도 잠금의 대기를 분석해 검사를 잠금 앞으로 옮기고 인덱스 추가, 처리 한계 초당 40~50건 → 60~90건
  • GitHub Actions + SSM으로 이미지 digest를 고정한 롤링 배포, 행사 중 서비스를 내리지 않고 5번 배포(배포 순간 연결 끊김 381건은 개선 과제)
  • 첫날 웹 푸시 미발송을 로그로 추적해 약 10시간 만에 수정, 3일간 서버 오류 0.002%(배포 시각 제외)

p95: 요청 100개 중 느린 쪽 5개 직전의 응답 시간. 평균이 감추는 "가끔 느린" 경험을 본다.

해결 과정

1. 느린 탐색 화면 — 쿼리별 DB 시간을 재서 고치기

k6 부하 테스트 · performance_schema · 서버 메모리 캐시

부하 테스트 느린 쪽 5% 응답 시간 0.98초 → 0.07초, 필요한 서버 4대 → 2대. DB 사양은 올리지 않았습니다.
문제
참가자 900명 + 채팅 450명을 15분 유지하자 p95가 0.98초, DB CPU 80%, 서버가 4대까지 늘었습니다. 서버를 더 늘리면 다음 한계는 DB 1대였습니다.
원인
측정하는 동안만 performance_schema를 켜서 쿼리별 DB 시간을 쟀습니다. 참가자 전원을 읽는 탐색 목록이 33%, 트랜잭션을 여닫는 명령(COMMIT, SET autocommit 등)이 약 25%였습니다.
해결
탐색 목록을 서버 메모리에 10초 보관하고, 만료되면 한 요청만 다시 읽게 했습니다. 읽기 전용 전환 명령을 DB로 보내지 않고 활동 시각 갱신을 서버 메모리에서 먼저 거르게 해, 운영 측정에서 요청 1천 건당 DB 명령을 40% 줄였습니다(로컬에서 콕 조회 1건: 19개 → 11개).

같은 조건(900 + 450명)에서 전후 비교

지표개선 전캐시 적용명령 축소까지
느린 쪽 5% 응답 시간(p95)0.98초0.19초0.07초

대가: 새 참가자와 프로필 수정이 다른 사람 화면에 최대 10초 늦게 보입니다. 서버마다 따로 보관해 서버끼리도 최대 10초 어긋납니다.

2. 행사 전체 콕 한도 — 정확성을 지키면서 처리량 올리기

MySQL 행 잠금 · 격리 수준 · 세마포어 · Testcontainers

부하 테스트 콕만 보낸 측정에서 처리 한계 초당 40~50건 → 60~90건. 콕이 몰려도 다른 기능(콕 목록 조회)의 보통 응답은 2초 → 21ms로 지켰습니다.
문제
행사 날에는 축제 참가자 전체의 하루 콕 수에 한도가 있습니다. 정확히 세려고 전용 잠금 행을 두자 모든 콕이 한 줄로 서게 됐고, 초당 50건부터 p95가 2초로 무너졌습니다. 기다리는 요청이 DB 연결을 쥐고 있어 콕과 무관한 기능까지 밀렸습니다.
원인
부하 중 잠금 대기를 2초마다 떠서 세 보니 453건 중 448건(99%)이 그 잠금이었고 DB CPU는 24%였습니다. DB가 바쁜 것이 아니라 잠금을 쥐는 시간이 길었습니다.
해결
실패할 요청은 잠금을 잡지 않도록 검사 6가지를 잠금 앞으로 옮기고, 건수 세기에 sent_at 인덱스를 넣었습니다. 잠금 뒤 건수가 앞선 전송을 모두 보도록 격리 수준을 READ COMMITTED로 바꿨습니다. 서버당 동시 4건 제한으로 나머지 DB 연결은 다른 기능 몫으로 남겼습니다.

표 1. 잠금 개선 전후 — 콕 전송의 p95(느린 쪽 5%)

운영 환경에 셋째 날 최악 데이터(콕 18,000행)를 넣고 쟀습니다. 제한 후 90건 구간에서는 27%가 "지금은 붐벼요"(429) 응답을 받았습니다. 정확성은 실제 MySQL에서 남은 다섯 자리를 열 쌍이 다투면 정확히 다섯 쌍만 성공하는지로 검증했습니다.

3. 믿을 수 있는 배포 — 서버를 한 대씩 바꿔 5번 배포

GitHub Actions · ECR · SSM · 이미지 digest · 롤링 교체

실제 운영 행사 중 서비스를 내리지 않고 5번 배포했습니다.
함께 봐야 할 한계 배포 순간 연결 실패가 381건 있었습니다. 컨테이너를 멈추기 전에 로드밸런서(ALB)에서 먼저 빼는 순서가 빠져 있었습니다. 다시 한다면 "ALB에서 빼기 → 연결 비우기 → 교체 → 확인 → 다시 등록" 순서로 고칩니다.
문제
:latest 이미지를 받고 ALB 정상 판정만 확인해, 두 서버가 다른 이미지를 받거나 새 프로세스가 죽어도 통과할 수 있었습니다. 배포 스크립트는 한 줄이 실패해도 계속 실행됐습니다.
해결
테스트를 통과한 뒤에만 이미지를 만들고, 그 digest(이미지의 지문)를 두 서버에 그대로 넘겼습니다. 서버를 한 대씩 교체하며 실행 중인 이미지가 방금 배포한 지문인지, 헬스체크가 UP인지 확인한 뒤에만 다음 서버로 넘어갑니다.

4. 첫날 웹 푸시 미발송 — 실패에서 배운 것

로그 추적 · 회귀 테스트 · AI 변경 리뷰

실제 운영 첫 실패 약 10시간 뒤 수정 배포, 이후 같은 오류 0건.
문제
첫날 푸시 발송 257건이 실패했지만, 콕과 채팅은 정상이라 겉으로 드러나지 않았습니다.
원인
로그로 추적해 보니 AI로 만든 다른 변경에서 암호화 제공자 초기화 순서가 바뀌어 있었습니다. 변경 목적만 보고 리뷰해 그 줄을 놓쳤습니다.
해결
초기화 순서를 바로잡고, 제공자가 없는 상태의 첫 발송을 재현하는 회귀 테스트를 더해 10/1 00:17에 배포했습니다. 이 일 이후 AI가 만든 변경은 diff 전체를 읽고 리뷰합니다.

구조

이 그림의 핵심 서버 2대가 같은 일을 나눠 하고, 데이터 원본은 MySQL 한 곳, 서버 사이 실시간 전달은 Redis가 맡습니다.

  • Spring Boot 서버는 자동 확장 그룹에서 2~4대로 돌고, 행사 내내 2대로 충분했습니다.
  • 접속 중인 사용자는 Redis에 90초 임대로 기록해, 서버가 죽어도 기록이 저절로 사라지게 했습니다(접속 중이면 웹 푸시 생략).

이 그림의 핵심 채팅은 MySQL에 먼저 저장하고, Redis 방송으로 다른 서버에 붙은 상대에게 전달합니다. 방송을 놓쳐도 화면이 이력과 대조해 채웁니다.

운영 결과

이 그래프의 핵심 3일간 요청 44만 건 동안 1분 단위 p95의 중앙값은 28ms였습니다.

검증

  • 테스트: 백엔드 455개(실제 MySQL 통합 테스트 포함), 프론트엔드 94개
  • 부하 테스트(k6): 900명 + 채팅 450명, 휴대폰 네트워크 환경 600명, 1시간 연속

남은 한계

  • 배포 순간 연결 실패 381건 — ALB에서 먼저 빼고 연결을 비운 뒤 교체해야 합니다.
  • 캐시는 서버마다 따로 보관해 서버끼리 최대 10초 어긋납니다.
  • 60~90건은 콕만 보낸 측정입니다. 다른 요청이 섞인 측정에서 행사 잠금 처리량은 초당 약 46~56건이었습니다.
  • 행사 한도는 DB 잠금으로 지켰습니다. 다시 한다면 Redis 카운터와 사후 대조를 검토합니다.
  • 혼잡 응답(429)을 받은 사용자에게 보여 줄 전용 안내 문구가 없었습니다.
